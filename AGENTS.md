# Enfyra isolated-vm fork

- This repository is the ISC-licensed `@enfyra/isolated-vm` fork. Keep the upstream copyright and LICENSE in every distribution.
- The native timer queue is owned by `src/lib/timer.cc`. There are two independent entry paths into the drain and both must stay non-recursive: a backlog of discarded/paused due timers inside `run_next()`, and `timer_t::chain()` re-entering from inside a timer callback. `run_next()` loops instead of recursing and raises `is_draining` while it holds the drain, so a callback's `chain()` becomes a no-op and the outer loop continues. Do not restore recursive `run_next()` ↔ `maybe_run_next()` traversal on either path, and do not let a callback re-enter the drain.
- Depth on both paths is driven by timers, not by the task cap. A task's deadline is shared only within that task: the Kernel computes `deadlineMs = Date.now() + timeoutMs` once per task, so every timed eval in it resolves to the same instant. It is **not** shared across a request — one request produces several tasks with different timeouts (a pre-hook batch at the 30s default and a handler batch at the route's own `timeout`, 60s default and 600s on the gateway routes). The discarded/paused backlog accumulates across a whole worker, so it can reach the 1,187 frames seen in the captured production core. Callback re-entry nests only on timers firing in the same sweep, and since a task runs its blocks sequentially it contributes at most one firing timer, so nesting is bounded by tasks sharing a deadline instant rather than by one task's block count. Measured callback-re-entry threshold on x86_64 musl is ≤192 always surviving, 256–320 intermittent, 400 always crashing, and `computeEngineTuning` caps production at 24–192 tasks per worker. A repro that creates hundreds of independent isolates each with its own timed eval overstates this path; production shares one deadline per task, not per isolate.
- `yarn test:timer-queue` covers both paths: a 12,000-timer cancelled backlog and 12,000 detached timers whose callbacks each call `timer_t::chain()`. Both regress to `SIGSEGV`/`SIGBUS` if either path is restored to recursion, so keep both scenarios in `test-timer-queue.cpp`. `CI=1 NODE_PATH="$PWD" yarn test` also runs the upstream suite; the CPU-profiler sampling case is intentionally skipped by its own CI guard.
- The `is_draining` fix is retained here deliberately even though the published `7.0.3` carries only the discarded-backlog half. Deploying it is not urgent: the backlog half is the path the captured production core points at and it is already live. Publish and roll out only on an explicit request.
- Release packaging must include both `prebuilds/linux-x64/isolated-vm.abi137.musl.node` and `prebuilds/linux-arm64/isolated-vm.abi137.musl.node` for Node 24 Linux musl. The server runtime image has no compiler. Verify the actual packed tarball loads on both image architectures without a build toolchain before publishing.
- Prebuilds are committed artifacts, so they do not rebuild when source changes. After any edit to `src/`, rebuild both prebuilds and confirm their hashes changed before publishing; a stale prebuild ships the old behaviour while the source in the tarball looks correct. Build inside `node:24-alpine` with `node-gyp rebuild --release --nodedir=/usr/local` (the local `node_modules/.bin/node-gyp` needs `--nodedir` to avoid downloading headers), then verify the packed tarball's extracted hashes match the binaries you tested.
- `.npmignore` uses explicit per-file patterns rather than a blanket `*.md`: `AGENTS.md`, `ISSUE_TEMPLATE.md`, and `native-example/README.md` are excluded, while `CHANGELOG.md` and `README.md` ship. A blanket `*.md` rule would also drop `CHANGELOG.md`.
- Kernel imports `isolated-vm` and pins the exact npm alias `isolated-vm: npm:@enfyra/isolated-vm@<published-version>`. Server does not import it directly; its installed Kernel owns the native dependency. Keep one addon version per process.
- Do not publish, commit, push, or deploy without the user's explicit request.
